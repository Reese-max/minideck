## Local verification

Use Node22. At the root install `npm ci`, then install each worker's lockfile
with `npm ci --prefix workers/presentation-studio-mcp` and the Runner equivalent.
Run root `npm run check`, root `npm run test:worker`, MCP `npm run check`, and
Runner `npx wrangler types` followed by `npm run check`. Root native browser
verification uses `npx playwright install --with-deps chromium` then
`npm run test:browser` (or an owned system binary via `CHROMIUM_PATH`).

The browser suite uses actual Chromium, the unchanged UI, local workerd and
native D1/R2; text generation and Turnstile transport return owned fixtures.
The V2 suite bundles the actual MCP handler, exercises modern 2026-07-28
Streamable HTTP tools (the canonical server explicitly rejects legacy clients),
native D1/R2, two synthetic immutable owners and token revocation, and rejects
all outbound transport. It queues work without starting AI generation. These
are local runtime controls, not deployed Cloudflare, real OAuth, full AI or
multi-user production acceptance. Final receipts must bind the clean Git tree;
historical upstream container/CI results remain separately attributed.

## Existing Preview is blocked before writes

The current legacy and MCP versions-upload jobs use their default config;
Runner selects `--env preview`. Those effective bindings share configured
production resources. All three Preview jobs now run
`node scripts/isolated-preview.mjs --audit-existing` before reading a credential
or performing a remote write. The audit deliberately fails on the current
shared configuration. Production job sections and trigger conditions retain
their original behavior. Draft checks do not enable deployment.

## Prepare an isolated plan without cloud writes

`config/isolated-preview.example.json` is deliberately invalid until an
operator supplies an approved fresh scope, two fresh D1 UUIDs and the matching
dedicated bucket. Never put credentials into that file. The legacy D1 must
differ from the studio D1; MCP and Runner must share the studio D1. A prefix
on a production/shared bucket is not isolation.

```sh
node scripts/isolated-preview.mjs --generate /owned/resource-plan.json
node scripts/isolated-preview.mjs --check .wrangler/isolated-preview/SCOPE
```

The generator only writes new local artifacts and refuses overwrite. Its
receipt remains `NOT_PROVISIONED_NOT_VALIDATED`, with original config hashes,
generated config hashes and the owned fixture seed hash. Reuse rejects drift.
It checks effective identity/bindings, aliases, service/workflow/DO references,
an exact fresh-only DO migration, asset scope, two matching queue consumers,
all polling/crons disabled and maximum one container instance. It excludes
production configured IDs/names and secrets. Syntax cannot establish actual
resource ownership/freshness: the operator must independently read back the
dedicated resource inventory and exact deployed identities before any write.

The generated site/MCP/Runner JSON files are standalone configurations, not
production configuration edits. The operator must separately approve resource
provisioning, migrations, fresh authentication and deployment. No account ID,
token, existing OAuth client, production profile, provider/router key or live
binding is copied. The router URL is empty, so this plan covers provider-free
stored fixtures only. Do not mark the Runner configured based on syntax.

For **fresh empty** resources, apply legacy `schema.sql` and the studio
`workers/presentation-studio-mcp/migrations/0001_init.sql`. The generated
`studio-seed.sql` inserts only an owned synthetic architecture/profile; it
deliberately conflicts on duplicate application and has no OAuth credentials.
Do not apply the legacy `0002` migration to a fresh schema that already has
publication columns. Existing legacy databases instead need the reviewed
publication migration/old-writer coordination described in the README; this
candidate performs neither operation remotely.

After explicit approval and resource readback, the operator can dry-run each
generated config, then deploy the dedicated components and validate the exact
published SHA, owner admission, native OAuth, job renewal/recovery, private
content boundaries and explicit publication using owned fixtures. Keep
polling off, do not connect paid providers, and record any new deployment
separately. Real rendering/full AI acceptance and approved production startup
for #11/#14 remain distinct later gates. A dry-run is not a verified Preview.
